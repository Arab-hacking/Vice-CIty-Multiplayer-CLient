# Архитектура

## Как вообще работает такой мультиплеер

GTA: Vice City — одиночная игра без сетевого кода и без API для модов.
Поэтому мультиплеер строится на трёх приёмах (так устроены SA-MP, VC-MP, MTA):

1. **Инжект DLL** — наш код живёт внутри процесса `gta-vc.exe`.
2. **Хуки и прямые вызовы функций игры по адресам** — мы просим саму игру
   создать педа/машину, двигать их, читать позицию локального игрока.
3. **Синхронизация состоянием, а не вводом** — клиент ~20–30 раз в секунду
   шлёт серверу «я в точке X, смотрю туда, скорость такая, HP столько».
   Сервер рассылает это остальным, и каждый клиент ставит у себя «куклу»
   (педа без ИИ) и двигает её по этим данным.

## Потоки данных

### Подключение игрока

```
Лаунчер: игрок выбрал сервер, ввёл ник
   │
   ├─ запускает gta-vc.exe (CREATE_SUSPENDED), инжектит vc-client.dll,
   │  передаёт: IP, порт, ник (командная строка / shared memory)
   ▼
Клиентская DLL: хуки поставлены, игра загрузилась в главное меню -> пропуск меню,
   подключение к серверу (UDP/ENet), handshake: версия протокола, ник, пароль сервера
   ▼
Сервер: проверил версию -> вызвал Lua-колбэк OnPlayerConnect ->
   отправил RPC: список игроков онлайн, машин, объектов, "заспавнься вот тут"
   ▼
Клиент: создал кукол всех игроков через функции игры, заспавнил локального игрока
```

### Игровой цикл синхронизации (каждый кадр)

```
[Хук главного цикла игры]  каждый кадр (~60 FPS)
   ├─ network_manager: принять пакеты сервера
   │     └─ sync_receiver: записать целевые позиции чужих игроков
   ├─ pools: интерполировать кукол к целевым позициям (плавно)
   ├─ sync_sender (не каждый кадр, а 20-30 Гц): отправить свою позицию/состояние
   └─ render (в хуке D3D8 EndScene): чат, никнеймы, скорборд
```

### Типы сетевого трафика

| Трафик | Частота | Надёжность | Примеры |
|---|---|---|---|
| Синхронизация пешком / в машине | 20–30 Гц | **ненадёжная** (потерялся пакет — не страшно, следующий уже летит) | позиция, скорость, поворот, HP, оружие, анимация |
| RPC (события) | по факту | **надёжная**, в порядке | спавн, смерть, вход в машину, создание объекта |
| Чат, команды | по факту | надёжная | `/me`, обычный текст |
| Выстрелы (bullet sync) | по факту | надёжная/быстрая | кто стрелял, откуда, куда попал (поздний этап) |
| Query (лаунчер ⇄ сервер) | по запросу | ненадёжная, отдельный лёгкий протокол | имя сервера, онлайн, пинг |

## Кто «главный» — модель доверия

Как и в SA-MP, на старте клиент в значительной мере **авторитативен о себе**
(своя позиция, своё HP сообщает сам клиент). Это просто и даёт играбельность,
но открывает дорогу читерам. Серверные проверки (телепорты, скорость, оружие)
и серверный пересчёт урона — отдельная поздняя задача (см. ROADMAP, этап 7).
С самого начала закладываем: сервер **может** отклонить невозможные данные
(например, скорость выше физически возможной) — API пулов на сервере это учитывает.

## Ключевые подсистемы клиента

- **Game layer** (`client/src/game/`) — единственный слой, знающий адреса игры.
  Остальной код работает через его классы (`CGame::CreatePed(...)` и т.п.).
  Если завтра поддерживаем exe 1.1/Steam — меняется только этот слой.
- **Pools** — соответствие «сетевой id ⇄ объект в игре» + интерполяция.
- **Render** — всё, что рисуется поверх игры. Через хук Direct3D8 (`EndScene`/`Present`)
  + ImGui на этапе разработки; позже можно перерисовать под стиль игры.

## Сервер

- Один процесс, консольный, тик ~50 мс: принять пакеты → обновить пулы →
  разослать синхронизацию тем, кто рядом (**streaming**: игрок получает данные
  только о тех, кто в радиусе ~200 м — иначе сеть и игра не вытянут 100 игроков).
- Игровой режим — Lua-скрипт: колбэки `OnPlayerConnect/Spawn/Death/Chat...`
  и функции API. Сервер без gamemode не стартует (как в SA-MP).
- Плагины на C++ через SDK — для тяжёлых вещей (MySQL, античит) — поздний этап.
